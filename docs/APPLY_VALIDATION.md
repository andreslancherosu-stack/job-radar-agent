# apply.py validation performed

2026-09-11/12: `python -m unittest discover -s tests -v` passed all 25 tests (9 pre-existing `radar.py` guardrail tests plus 16 new `apply.py` guardrail tests covering the submit-button denylist, profile-path resolution including list indices, missing-answer collection, and plan-approval/action-allowlist enforcement). None of these require a browser.

Separately, `apply.py fill` was run against the local `testapp/` fixture (served via `python -m http.server`) using a fictional plan and profile (`demo/apply_plan_testapp.json`, `demo/test_profile.json`), with these observed, measured outcomes:

- **Happy path**: a complete fictional profile was filled across all three input pages (personal info, education/employment, screening/documents including a file upload), each value re-read from the live page immediately after being set. The run stopped at the review page with status `awaiting_review` and never clicked `#submit-application-btn`. Verified independently by reopening the same run's browser profile and reading the rendered review page: all fields matched the source profile, the submit button was not disabled, and the "submitted" banner was not shown.
- **Missing information**: a profile with `work_auth` set to `null` was rejected before any browser was opened. The run stopped with status `paused_missing_info` and one item in `missing_questions` naming the unanswered question. Supplying a complete profile under the same run key then completed normally to `awaiting_review`.
- **Real validation error and resume**: a profile with the required certification checkbox left unchecked passed the pre-flight check (the field has a value, just not the required one) and was correctly rejected by the fixture's own client-side validation after page 3. `apply.py` captured the exact message ("You must certify the information is accurate.") and stopped with status `blocked_validation`, without advancing. Re-running `fill` with the same run key and a corrected profile resumed directly on page 3 — the action log shows no re-filling of pages 1-2 — and reached `awaiting_review`. Reading the review page afterward confirmed the page 1/2 data (name, address, education, employment) was still intact, proving it survived across two separate process invocations via the run's persistent on-disk browser profile, not just an in-memory session.
- **Optional marketing consent**: the plan does not include a step for the fixture's "Send me marketing emails" checkbox. The review page after every run above confirms it read "No" (unchecked), demonstrating the tool does not opt into optional consent on its own.

Not yet tested: any real employer or ATS page; a form requiring more repeated entries than the plan lists (the plan does not click "Add Another" rows automatically); a real login/MFA/CAPTCHA interruption; multi-file uploads; a form whose validation errors are not rendered as visible text.

## 2026-09-25 additions

`python -m unittest discover -s tests -v` now passes all 59 tests (25 above, plus 34 new: 10 for `import_posting.py`, 8 for `answers.py`, 4 for `coverletter.py`, 7 for `llm_client.py`, and 6 more added to `test_apply.py` for the answer-bank and duplicate-detection extensions). Only `test_coverletter.py`'s docx round-trip and the live checks below touch real I/O; the rest are pure logic, no network, no browser.

- **Job-URL import, real network**: `import_posting.py fetch https://example.com ...` performed a genuine HTTP GET (not a canned fixture), extracted "Example Domain..." text, and correctly flagged it as short via the same heuristic used for real postings — a true positive, not a false one, since example.com's body is in fact ~127 characters.
- **Answer bank wired into apply.py, live**: a plan variant sourcing one field (`LinkedIn Profile URL`) from `"answerbank:LinkedIn Profile URL"` was run against `testapp/` with a confirmed bank entry whose answer deliberately differed from the profile's own value. The review page afterward showed the answer-bank value, not the profile's — confirming the new `resolve_value` prefix is actually reached and used during a real fill, not just accepted by a unit test.
- **Duplicate-application refusal, live**: `apply.py fill ... --job-key K --radar-state STATE` against a state file recording `K` as already applied stopped immediately with status `blocked_duplicate`, `current_url: null`, and a single action-log entry — no browser was opened. The same command with a key not in that file's `applications` proceeded normally to `awaiting_review`. (First attempt at this test used a monkeypatched module constant to point at a fixture state file and silently didn't work, because Python binds a `def f(x=SOME_GLOBAL):` default at import time, not call time — `already_applied`/`run_fill` were changed to accept `radar_state_path` as a real parameter instead, and the CLI grew `--radar-state` to match, mirroring `radar.py`'s own `--state` flag.)
- **Cover letter pipeline**: `generate` correctly refuses to run before `approve` (`ValueError`); after `approve`, `generate` produces a real `.docx` via `python-docx` and a genuine read-back-and-compare confirms the extracted paragraph text matches the approved text exactly.
- **Streamlit UI, live in a real headless browser** (not just "the server started"): loaded `ui.py` with Playwright/Chromium against the actual running Streamlit process. In real (non-demo) mode it rendered "No postings ingested yet" with no traceback. Toggling to demo mode in that same live session correctly re-rendered the fictional shortlist, the selected posting's fit evidence and quotes, and the Fill-application controls — proving the subprocess-and-JSON-file wiring, not just that the page loads. One real bug was caught this way and fixed before commit: `st.dataframe(..., use_container_width=True)` is deprecated in the installed Streamlit (1.64.0) and was replaced with `width='stretch'`.
- **Standalone LLM integration**: `llm_client.py`'s output schema is unit-tested to stay in lockstep with `radar.DIMENSIONS`/accepted status and fit values, and `assess_with_llm` is confirmed to raise a clear `RuntimeError` (no network call attempted) when no key is present. `python llm_client.py check` in this environment reports `"anthropic_api_key_configured": false` — the live API call itself has not been exercised here; that remains a real, reported gap, not a claimed success.

Still not tested: any of the above against a real employer posting or real personal data; `llm_client.py`'s actual network call (no API key available in this environment); a cover letter drafted and approved for a real application.
